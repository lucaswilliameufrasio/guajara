# Releasing

Guajará uses SemVer tags (`vX.Y.Z`) and `cargo-dist` to build platform archives,
SHA-256 checksums, shell and PowerShell installers, and GitHub Releases. Releases
are not published to crates.io.

## One-time GitHub setup

1. Under **Settings → Actions → General → Workflow permissions**, allow read and
   write permissions and enable GitHub Actions to create pull requests.
2. Create an environment named `release` under **Settings → Environments**.
   Add required reviewers if release preparation should wait for approval.

The `Prepare Release` workflow uses this environment and the repository's
`GITHUB_TOKEN` to open a release preparation PR.

## Standard release

1. Run **Actions → Prepare Release → Run workflow** on `main`, entering the next
   stable version (for example, `0.3.0`). The workflow updates `Cargo.toml`,
   `Cargo.lock`, and `CHANGELOG.md`, then opens a PR.
2. Review the PR and wait for CI. Merge it only after the version and changelog
   are correct.
3. Update local `main` and push the matching tag:

   ```bash
   git checkout main
   git pull --rebase
   git tag v0.3.0
   git push origin v0.3.0
   ```

4. The `Release` workflow builds Apple Silicon macOS, Linux (ARM64 and x64),
   and Windows (x64) artifacts, generates checksums and installers,
   and publishes the GitHub Release.

## Bootstrap the existing v0.2.0 tag

The `v0.2.0` tag predates this workflow. After the release workflow is merged to
`main`, run **Actions → Release → Run workflow** from `main` and enter
`v0.2.0`. The workflow verifies the tag version and confirms that its source,
dependencies, and lockfile still match before publishing. It targets the
existing tag commit and does not recreate or move the tag.

This manual recovery input only works while the current package version still
matches the tag. New releases should use the normal tag-push flow above.

## cargo-dist configuration

`dist-workspace.toml` defines the target platforms and installers.
`.github/workflows/release.yml` is generated by cargo-dist and has reviewed
customizations for pinned GitHub Actions, the Bash shell used by the cross-platform
artifact build step, and the one-time existing-tag recovery input. Because
`allow-dirty = ["ci"]` preserves those changes, review them if regenerating or
upgrading cargo-dist.
